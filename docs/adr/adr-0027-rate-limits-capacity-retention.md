# ADR-0027 — Rate limits, capacity и retention (этап 9)

Статус: Accepted. Этап 9 миграции (`Rate Limits and Capacity Planning`,
§39–§46, §59–§62, §66, §68, §70, §88). Опорные документы: аудит
`docs/migration/audits/HOSTING_MIGRATION_AUDIT.md`, результаты этапов 2–8,
тесты `tests/test_stage9_limits_capacity.py`, код `backend/capacity.py`.

## 1. Контекст

К этапу 9 приложение — мультиюзерный хостед-сервис на целевой ёмкости
**~1000 зарегистрированных пользователей (20–30 учителей) на VPS
1 vCPU / 1 GB** (§88), но:

- `/api/auth/login`, `POST /api/sync` и `DELETE /api/cache` были
  неограничены: публичный сервис меняет threat model (§39);
- `SYNC_MAX_WORKERS=16` остался от одно-пользовательского desktop и при
  умножении на число одновременных синков даёт неподтверждённый бюджет
  потоков/квот (§40);
- не было посчитано, сколько запросов к Classroom реально делает
  1000 пользователей (§88);
- у «удаления данных» не было механизма: ни retention для мёртвых
  сессий/попыток логина, ни пути «удали мой аккаунт» (§44);
- `_do_sync` держал SQLAlchemy-сессию открытой через весь сетевой фетч
  к Google — на PostgreSQL это держало бы соединения пула (§45).

## 2. Решение: rate limiting (§39)

**In-memory token buckets, только hosted, ключ `(поверхность, client IP)`.**

| Поверхность | Дефолт | Ответ при превышении |
| --- | --- | --- |
| `GET /api/auth/login` | 30/мин/IP | 429 + `Retry-After` |
| отклонённые `GET /api/auth/callback` | 20/мин/IP | redirect `/?login_error=429` |
| `POST /api/sync` | 60/мин/IP **+ cooldown 60 с на пользователя** | 429 + `Retry-After` |
| `DELETE /api/cache`, `/api/me/cache` | 10/мин/IP | 429 + `Retry-After` |

Ключевые свойства:

- bucket'ы лежат в `app.state.rate_limiter` (одна registry на приложение):
  два app-инстанса в одном процессе не делят квоту, тесты изолированы;
  clock внедряемый — тесты не спят;
- IP берётся из `X-Forwarded-For` **только** если пир в
  `GC_DASHBOARD_TRUSTED_PROXIES` (`proxy.client_ip`), иначе — TCP-пиры:
  подделать свой «IP» нельзя; это throttle-ключ, не решение доступа;
- throttling **только success-поверхностей входа и фан-аута**: удачные
  callback'и не считаются (школьный NAT не упирается в лимит);
- ручной синк дополнительно ограничен **per-user cooldown**
  (`SYNC_MANUAL_COOLDOWN_SECONDS`, §39): держащий кнопку пользователь
  получает 429, а не второй фан-аут к Classroom; фоновый планировщик
  cooldown не проходит;
- desktop-путь middleware не трогает (§74) — одному локальному
  пользователю лимиты не нужны.

Redis/маршрутизатор-лимитеры не вводились: при первой реплике in-memory
достаточно, а §88 прямо запрещает добавлять компоненты «на всякий
случай». При горизонтальном масштабировании buckets считаются на
реплику — это осознанное ограничение (см. §8).

## 3. Решение: квоты и capacity (§40/§88)

**Консервативные дефолты + измеряемая арифметика вместо допущений.**

- `SYNC_MAX_WORKERS`: **16 → 4** (per-user пул потоков);
  `SYNC_MAX_CONCURRENT_USERS` остаётся **2** → бюджет воркера
  **4 × 2 = 8 потоков** (`capacity.sync_thread_budget`);
- оценка в коде, а не в прозе (`backend/capacity.py`):
  `avg ≈ (users × 5 + teachers × 40) / interval` → **1500 юзеров + 100
  учителей** / 30 мин (прод-интервал) ≈ **383 запроса/мин ≈ 6.4 QPS** —
  порядок ниже per-project квоты; per-user пул 4 ≪ per-user квоты.
  Константы `TARGET_USERS`/`TARGET_TEACHERS` обязаны совпадать с заголовком
  `compose.yml`, иначе цифры описывают не тот deployment (тест
  `test_capacity_target_matches_the_compose_header`);
- наблюдаемость вместо максимизации: `RequestStats` считает
  `requests` / `quota_errors` (429 и quota-403) / `server_errors` (5xx) и
  пишет их в строку синка; рост лимитов — только вместе с этими
  счётчиками;
- teacher-синк считается дороже студенческого и размазан stagger'ом
  (§64) и bounded-очередью (§18), поэтому пики гасятся без новых
  компонентов;
- PostgreSQL-пул мал: `pool_size=5`, `max_overflow=5`, `pool_recycle=1800`
  — возможно потому, что синк больше не держит соединение через фетч.

## 4. Решение: ошибки токенов, логи, privacy, retention (§41–§45)

- **§41:** `invalid_grant` при рефреше удаляет **только строку
  `oauth_tokens` этого пользователя** (остальные гранты и сессии живы),
  401 посреди синка → `needs_reauth` + удаление своего гранта; повторных
  попыток мёртвого гранта нет, «разлогинить всех» — нельзя.
- **§42:** hosted-процессы пишут логи в **stdout** (Docker/systemd);
  `access_log.RedactSecretsFilter` вырезает token/cookie/secret-формы из
  любых записей (`access_token=…`, `Bearer …`, `ya29.…`), оставляя
  операционные поля; query-редакция access-log — из этапа 8; desktop
  остаётся на `logs/app.log`.
- **§43:** новых чувствительных полей не добавлено; email ростера по-прежнему
  опционален (scope не расширялись); удаляя аккаунт, удаляются и ростер, и
  оценки этого пользователя (каскад).
- **§44:** политика retention задана явно (таблица в
  `maintenance.py`): сессии 14 суток + sweep (`RETENTION_SWEEP_SECONDS`,
  воркер), OAuth-попытки 15 минут, кэш — до следующего синка/очистки/
  удаления, `last_sync` всегда на виду (§61). Пути удаления:
  `DELETE /api/me/google` (отвязать Google, оставить аккаунт) и
  `DELETE /api/me` (аккаунт целиком: сессии, токены, sync-состояние,
  кэш) — оба с `confirm=true`, оба **только про вызывающего**; глобального
  «стереть всё» по-прежнему нет.
- **§45:** `_do_sync` разложен на фазы с короткими транзакциями:
  claim+креденшелы → **сессия закрывается** → сетевой фетч без открытого
  соединения → запись (коммит на курс) → purge/mark; воркеры не делят
  Session; пул мал и с `pool_pre_ping`/`pool_recycle`.

## 5. Решение: конкурентные правила (§46)

| Сценарий | Механизм |
| --- | --- |
| один пользователь, две вкладки | одна HttpOnly-cookie-сессия (`sessions`) |
| два одновременных OAuth-callback | per-attempt state в БД, одноразовый, привязан nonce-cookie (этап 2) |
| параллельный refresh одного токена | per-user `_refresh_lock_for` (этап 4) |
| два клика «Sync» | claim в БД + per-user лок → 409; cooldown → 429 |
| ручной + фоновый синк | один `claim_sync` — выполняется ровно один |
| синки разных пользователей | независимые локи/джобы: A не блокирует B |
| одинаковый Google course id у двух | user-scoped PK `(user_id, id)` (этап 3) |

## 6. Решение: ошибки, метрики, кэш, индексы, время (§59–§70)

- **§59:** публичные ответы — короткие фразы по статусу (401/403/404/409/
  429/502/503), raw-исключения/трейсы/SQL не возвращаются; полный стек —
  только в серверный лог.
- **§60:** `metrics.py` — счётчики по именам событий (login ok/fail,
  logout, отклонённые сессии, sync ok/fail/needs_reauth, крахи джобов,
  вычищенные сессии), периодическая строка `metrics[worker] …` из цикла
  воркера; + `quota_errors/server_errors` из `RequestStats`; в ключах
  счётчиков нет персональных данных.
- **§61:** авторитет — Google Classroom; PostgreSQL — кэш; после
  неудачного синка кэш остаётся, `last_sync`/`last_sync_error`/`sync_status`
  всегда отражают возраст данных (устаревшее не выдаётся за свежее);
  устаревание не «сгорает» по TTL — следующая синхронизация сверяет;
  archived-курсы скрыты; удаления отражаются зеркальным purge.
- **§62:** все ключи — `(user_id, …)`: таблицы кэша (этап 3), кэш профиля
  и рейт-лимиты по локальному id/IP; Google-id голым ключом нигде не
  является; будущий Redis-кэш наследует то же правило.
- **§66:** `DELETE /api/cache?confirm=true` user-scoped ещё с этапа 3,
  добавлен явный алиас `DELETE /api/me/cache`; оба — 400 без `confirm`,
  оба за session-gate/CSRF-проверкой.
- **§68:** ревизия индексов — Alembic `0003`: составной
  `sessions(user_id, expires_at)` вместо одноколоночного `user_id`;
  остальные кандидаты §68 уже покрыты PK с `user_id` префиксом и
  `ix_coursework_user_course`/`ix_cw_submission_user_course` — слепых
  индексов не добавлено, тест фиксирует и состав, и правило.
- **§70:** время — **naive UTC во всех таблицах и сравнениях** (как и
  раньше); сервер живёт в UTC, due-даты Classroom остаются naive-локальными
  (ADR-0004), рендер в локальной зоне — на фронте (`dates.toLocalDate`,
  этап 7). Миграция таймзон не требуется: ни одна колонка не меняла
  семантику; DST на сервере не применяется к stored-значениям.

## 7. Последствия

- Новые env: `GC_DASHBOARD_RATE_LIMIT_*` (4),
  `GC_DASHBOARD_SYNC_MANUAL_COOLDOWN_SECONDS`, `GC_DASHBOARD_RETENTION_SWEEP_SECONDS`,
  `GC_DASHBOARD_DB_POOL_SIZE`, `GC_DASHBOARD_DB_MAX_OVERFLOW`; дефолт
  `GC_DASHBOARD_SYNC_WORKERS` изменён 16 → 4 (в `.env.example` явно).
- Новые поверхности API: `DELETE /api/me`, `DELETE /api/me/google`,
  `DELETE /api/me/cache` (все user-scoped, `confirm=true`).
- Нагрузочный тест на живом PostgreSQL (RAM/CPU/latency/queue depth)
  и фактическая сверка `google_requests` с оценкой `capacity.py` —
  **этап 10**; гейт роста лимитов — счётчики quota_errors из логов.
- Ограничение: buckets на реплику; при выходе на несколько реплик лимит
  считается суммой — пересмотреть вместе с §88 (вертикальное масштабирование
  остаётся первым шагом).
