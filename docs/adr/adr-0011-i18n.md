# ADR-0011: Мультиязычность (en/uk/ru) через собственный типизированный i18n

Дата: 2026-09-14
Статус: Accepted

## Контекст

Интерфейс был написан на английском. Пользователь попросил добавить украинский
и русский языки. Проект небольшой, зависимостей минимум (ADR-0005), а язык —
это пользовательская настройка, которая уже есть где хранить (ADR-0006).

## Решение

- **Собственный i18n без зависимостей** (`frontend/src/i18n.ts`):
  плоские словари с семантическими ключами (`nav.dashboard`,
  `dash.noToday`), интерполяция через `{name}`-плейсхолдеры, хук
  `useI18n()` → `{ t, language, setLanguage, locale }`.
- **Английский — источник истины**: `const EN = { ... } as const` даёт
  `type I18nKey = keyof typeof EN`; украинский и русский объявлены как
  `satisfies Record<I18nKey, string>`, поэтому **пропущенный или лишний ключ
  не компилируется** (`tsc` падает на сборке, а не в рантайме).
- **Хранение выбора** — в `AppSettings.language` (localStorage, ADR-0006).
  При первом запуске язык определяется по `navigator.language`
  (`detectLanguage()` → uk / ru / en), дальше — только явный выбор
  пользователя.
- **Локализация дат** — модульная локаль в `dates.ts`: `setLocale()`
  вызывается из `SettingsProvider` при смене языка, форматтеры
  (`formatDate`, `formatTime`, `formatDateTimeShort`) и календарные подписи
  (`toLocaleDateString`, названия дней недели) используют BCP-47 локаль
  `LOCALE: en-US / uk-UA / ru-RU`. `relativeDayLabel()` больше не возвращает
  готовые строки, а отдаёт `{ key, count }`, который страница прогоняет через
  `t()` — так один и тот же «Today/Tomorrow/…» локализуется везде.
- **Без цикличных импортов**: `i18n.ts` зависит от `SettingsContext`
  (язык) и `dates.ts` (локаль); локальные утилиты (`LOCALE`,
  `detectLanguage`, `setLocale`) живут в `dates.ts`, а `SettingsContext`
  знает только про `dates.ts` — граф зависимостей ациклический.
- **Переключатель языка** — в Настройках → «Внешний вид» → «Мова/Язык/…»
  (`English / Українська / Русский`). Заголовок вкладки браузера
  (`document.title`) обновляется через `t("app.title")` в `AppShell`.
- **Язык документа** (`<html lang>`) следует за тем же выбором и ставится
  одним владельцем — `SettingsProvider`; до первой отрисовки его ставит
  `public/prepaint-init.js`, потому что статический `lang="en"` в
  `index.html` иначе успевает отрисоваться (ADR-0034).

## Последствия

- Добавление нового языка = один словарь + одна запись в `LOCALE` и
  `LANGUAGE_OPTIONS`; компилятор сам покажет все недостающие ключи.
- Все пользовательские строки UI проходят через `t()`; в коде остаются только
  данные из Google (названия курсов/заданий) и технические детали.
- Строки, приходящие от бэкенда (детали ошибок API), не переводятся — это
  диагностические сообщения, а не UI-контент; интерфейсные формулировки вокруг
  них локализованы.
- Плюрализация сделана двумя ключами (`nav.overdue.one` / `.many`) без
  библиотеки плюралов — для трёх языков и одного счётчика этого достаточно;
  при росте числа счётчиков это первое, что стоит пересмотреть.

## Альтернативы

- `react-i18next` — отклонено: ~40 КБ и конфиг ради трёх словарей и одного
  пространства имён.
- `@formatjs/intl` (ICU-сообщения) — отклонено: правильная плюрализация и
  форматирование, но избыточно для текущего объёма строк.
- Готовые строки прямо в компонентах с условием по языку — отклонено:
  невозможно проверить полноту перевода, ключи дублируются в каждом файле.
