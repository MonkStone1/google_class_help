# ADR-0015: Фоновая синхронизация — при старте, по расписанию и после входа

Дата: 2026-09-15
Статус: Accepted
Связанные: [ADR-0003](adr-0003-sqlite-cache-and-sync.md), [ADR-0014](adr-0014-parallel-staged-sync.md)

## Контекст

До сих пор sync запускался только вручную кнопкой **Sync** (`POST /api/sync`).
После перезапуска бэкенда дашборд открывался на устаревшем кэше; если
пользователь забыл нажать кнопку, данные могли отставать на дни. Ручной sync —
по-прежнему единственный источник актуальности, и это неудобно для
локального всегда-открытого дашборда.

Требования: синхронизация при старте приложения, затем автоматически каждые
10 минут (интервал должен быть настраиваемым), плюс немедленный sync после
успешного входа в Google, чтобы дашборд не пустовал до ближайшего тика.

## Решение

Новый модуль `backend/background_sync.py` (демон-поток, живёт вместе с
процессом uvicorn — приложение запускается одним процессом, см.
`Classrom_dashboard.bat`):

- `main.on_startup()` после `init_db()` вызывает `background_sync.start()`:
  первый sync выполняется сразу, далее цикл повторяется каждые
  `SYNC_INTERVAL_MINUTES` минут;
- интервал задаётся переменной окружения
  `GC_DASHBOARD_SYNC_INTERVAL_MINUTES` (по умолчанию 10, некорректное
  значение откатывается к 10; `0` полностью выключает расписание — и стартовый
  sync тоже);
- `auth._run_login_flow()` после успешного consent вызывает
  `background_sync.request_soon()` (отложенный импорт разрывает цикл
  `auth ← sync ← background_sync`);
- все запуски идут через `sync.sync_now()` с её потоковым мьютексом:
  фоновый запуск никогда не дублирует ручной и наоборот; одноразовые
  триггеры исполняются сериальным исполнителем на один поток и не
  накапливаются;
- поток — daemon: при остановке uvicorn (`--reload`, Ctrl+C) ничего не
  нужно останавливать вручную; `stop()` существует для тестов;
- каждый запуск печатает одну строку результата в консоль бэкенда
  (`[background-sync] scheduled sync ok/failed: …`) — локальная
  наблюдаемость без настройки логирования.

Не подписан в Google: `sync_now()` возвращается сразу с «Not signed in»,
ошибка не пишется в `last_sync_error` и не тревожит UI; следующий тик
повторяет попытку (то же самое при офлайне — ошибки фиксируются
самим sync в `sync_state.last_sync_error`, как в ADR-0003).

## Последствия

- Дашборд всегда открывается на данных не старше последнего тика (≤10 минут),
  а сразу после запуска бэкенда кэш обновляется без участия пользователя.
- Ручная кнопка **Sync** сохраняется для принудительного обновления; мьютекс
  гарантирует «синхронизация уже идёт» вместо дублирования.
- Нагрузка на Classroom API растёт умеренно: один полный sync каждые
  10 минут (при ~800 запросах — порядка 1–2 QPS в среднем), что на порядок
  ниже пер-юзерской квоты 20 QPS из ADR-0014.
- `on_event("startup")` в FastAPI объявлен устаревшим в пользу lifespan;
  оставлен существующий механизм ради единообразия кода.

## Альтернативы

- Синхронизация на каждый запрос фронтенда (если данные устарели) — отклонено:
  рассинхронизация параллельных запросов, лишние запуски sync (ADR-0003 уже
  отклонял sync при каждом открытии).
- `asyncio`-таск вместо потока — отклонено: `sync_now()` блокирующий
  (сеть + SQLite), пришлось бы всё равно уходить в executor; поток проще.
- APScheduler / celery — отклонено: зависимости ради одного интервального
  цикла в локальном приложении.
- Синхронизация только на старте без повтора — отклонено: при долгой
  сессии данные снова устаревали бы без ограничений.
