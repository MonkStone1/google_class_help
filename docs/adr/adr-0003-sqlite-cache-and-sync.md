# ADR-0003: SQLite-кэш и стратегия синхронизации

Дата: 2026-09-14
Статус: Accepted

## Контекст

UI должен открываться мгновенно, переживать недоступность Google/интернета и
не генерировать лишние запросы к Classroom API. Нужен локальный кэш.

## Решение

- SQLAlchemy 2.0 + SQLite в `data/classroom.db`. Таблицы: `courses`,
  `coursework`, `submissions` (составной PK course_id + coursework_id),
  `sync_state` (last_sync, last_sync_error).
- Синхронизация — полная и зеркальная: курсы → преподаватели → courseWork →
  submissions по каждому заданию, с пагинацией. Апсёрты по первичным ключам,
  поэтому повторный
  sync не создаёт дублей.
- Синхронизация запускается вручную кнопкой **Sync** (`POST /api/sync`) и
  защищена потоковым мьютексом: второй одновременный запрос получает
  «синхронизация уже идёт», а не дублирует выгрузку.
- `last_sync` хранится в БД и показывается в топбаре («Last synchronized: …»).
- При ошибке сети/Google: ошибка записывается в `sync_state.last_sync_error`,
  UI показывает дружелюбное сообщение и продолжает работать на кэше.
- Очистка кэша — `DELETE /api/cache?confirm=true`, только с явным
  подтверждением в UI (деструктивное действие).

## Последствия

- Полный sync — O(курсы × задания) запросов. Для личного аккаунта (единицы
  курсов, десятки заданий) это секунды; инкрементальная синхронизация по
  `updateTime` признана преждевременной оптимизацией.
- Схема БД простая, без миграций: `Base.metadata.create_all` на старте. Для
  личного приложения достаточно; при изменении схемы файл кэша можно удалить
  и пересинхронизироваться.

## Альтернативы

- Синхронизация при каждом открытии дашборда — отклонено: лишние запросы и
  медленный старт при офлайне.
- JSON-файл вместо SQLite — отклонено: нет частичных обновлений и индексов.
