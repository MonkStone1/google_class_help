# ADR-0035: Тикеты обратной связи и allow-list администраторов

- **Статус:** Accepted
- **Дата:** 2026-10-01

## Контекст

У сервиса нет способа получать обращения пользователей: всё общение идёт
внешними каналами, а поддержка не может ни увидеть историю разговора, ни
отметить проблему решённой. Референсный продукт (скриншоты в
`docs/prompt/feedback_update/`) показывает структуру: категория, тема,
Markdown-сообщение, вложения, ответ поддержки.

Дополнительные ограничения, которые решение обязано учесть:

- **Аутентификация неприкосновенна.** `get_current_user` (ADR-0022) —
  единственный способ узнать, кто 调用; личность приходит из сессии, а не из
  формы (ADR-0020).
- **CSP запрещает CDN** (§38/§48): `script-src 'self'`, без удалённых
  ресурсов — значит редактор Markdown подключается локально.
- **Загрузок в проекте не было.** `Caddyfile` прямо утверждал, что функции
  загрузки нет; добавление первого upload-механизма требует минимально
  безопасного, а не «удобного» дизайна.
- **Хостинг — 1–2 vCPU VPS** за Cloudflare Tunnel с одной репликой web.

## Решение

### 1. Домен и изоляция

Три таблицы с каскадом от `users.id` (миграция `0004`):

```
users ─┬─ feedback_tickets ─┬─ ticket_messages ── ticket_attachments
       │                    └─ ticket_attachments (денормализованный ticket_id)
```

- `feedback_tickets.user_id` → `users.id` `ON DELETE CASCADE`. Право владения
  структурно: чтение фильтрует по `user_id` **внутри** одного SELECT, поэтому
  чужой тикет неотличим от несуществующего (404, не 403 — §23/§12).
- `ticket_messages.author_user_id` — **всегда** сессионный пользователь.
  `author_type` (`USER`/`ADMIN`) — машинно-читаемое различие, по которому UI
  рисует сообщения; `display_name` — только публичная подпись.
- `ticket_attachments.ticket_id` выводится сервером из `message_id`, поэтому
  проверка прав при скачивании — один индексный lookup, а не join.

### 2. Администраторы — allow-list из окружения

> **Superseded (ADR-0036).** Этот раздел описывает `ADMIN_EMAILS` — источник
> авторизации обычных администраторов. Переменная **удалена** и больше ничего не
> разрешает: обычные администраторы теперь хранятся в таблице `admins` и
> управляются через `/admin/admins`, а `SUPER_ADMIN_EMAIL` задаёт единственного
> Super Admin. Раздел оставлен как часть истории решения; ниже — то, что
> заменило его.

```python
ADMIN_EMAILS: frozenset[str] = frozenset(
    email.strip().lower() for email in _csv_env("ADMIN_EMAILS") if "@" in email
)
```

- **Fail closed:** пусто/не задано ⇒ администраторов нет.
- Без префикса `GC_DASHBOARD_` — как `COOKIE_SECURE`, `APP_BASE_URL`,
  `TURNSTILE_SITE_KEY`: это значение авторизации, а не ручка тюнинга.
- Только серверное окружение. **Никогда** не `VITE_*`, не поле конфига, не
  ответ API: фронтенд получает один булев `UserOut.is_admin`, вычисленный той
  же функцией `config.is_admin_email`, что и `admin_auth.require_admin`.
- Нет ролей в БД, нет «первый пользователь = админ», нет wildcard.

### 3. Ответ открывает решённый тикет

Новое сообщение в тикете со статусом `resolved` переводит его в
`in_progress`. Альтернативы («оставить закрытым», «спросить подтверждение»)
отвергнуты: первая молча проглатывает ответ пользователя, вторая требует
лишнего состояния и ветки API. Правило видимо в UI — пользователь сразу видит,
что тикет снова активен.

### 4. Удаление окончательное

`DELETE /api/admin/feedback/tickets/{id}` → 204: строка удаляется,
`ON DELETE CASCADE` уносит сообщения и строки вложений, файлы снимаются с
тома `appdata`. Без `deleted_at`, без soft-delete, без восстановления.
Подтверждение живёт во **фронтенде** (настоящий React-диалог, не
`window.confirm`): бэкенд не может задать вопрос, поэтому просто выполняет
удаление.

### 5. Вложения

Первый upload-механизм проекта, поэтому минимально безопасный вариант:

- **Тип определяется содержимым** (magic numbers; для `text/plain` —
  декодируемость UTF-8), никогда — расширением или `Content-Type` клиента.
  Хранится под расширением **распознанного** типа.
- Активное содержимое и исполняемые файлы отвергаются по имени, включая
  двойные расширения (`.html.exe`, `.pdf.zip`).
- Лимиты проверяются **по ходу стриминга**, тело не буферизуется целиком:
  3 файла на сообщение, 5 МБ на файл, 10 МБ суммарно.
- Файлы лежат на томе `appdata` (`DATA_DIR/feedback/<ticket_id>/`) под
  серверным именем (`uuid4` + каноническое расширение); каждый путь
  проверяется на выход за пределы корня.
- Раздача — **авторизованный endpoint** `GET /api/feedback/attachments/{id}`
  с `Content-Disposition: attachment` и `nosniff`. Статического mount для
  загрузок нет: `frontend/dist` — единственный статический mount, и SPA
  fallback выдал бы всё, что найдёт.
- `Caddyfile`: `request_body max_size` поднят с 2MB до **16MB** — с запасом
  над 10 МБ вложений плюс поля формы.

### 6. Markdown хранится как есть

`body_markdown` — недоверенный исходник; бэкенд не экранирует и не чистит
его (иначе сохранённое значение врало бы). Санитизация — на отрисовке,
`rehype-sanitize` в редакторе и в read-only рендерере; `dangerouslySetInnerHTML`
не используется.

### 7. Лимиты

Per-USER токен-бакеты (`feedback:create:{id}` / `feedback:reply:{id}`) в том же
`app.state.rate_limiter`, что и login/sync/cache: школьный NAT делит один IP
между легитимными пользователями, и IP-лимит наказывал бы не тех. Поверх —
грубый per-IP предел в `throttle_abuse_surfaces`, чтобы один адрес не
заливал multipart в единственную реплику web.

## Последствия

**Хорошие**

- Изоляция пользователей проверяется тестом на уровне схемы и API; тикет
  чужого пользователя физически неотличим от отсутствующего.
- Аудит ответов сохраняется: два администратора публикуют под разными именами,
  но `author_user_id` у обоих верный.
- `delete_user_data` (ADR-0027) удаляет и тикеты, и их файлы, и не трогает
  чужие строки.

**Плохие / ограничения**

- Файлы живут на томе `appdata`: потеря тома теряет файлы при живых строках
  БД (и наоборот). Это осознанный размен — объектное хранилище в проекте нет.
- Ограничитель in-memory и привязан к процессу: одна реплика web (это уже
  требование compose.yml), при масштабировании понадобится общее хранилище.
- Удаление необратимо: восстановить тикет нельзя, только заново создать.
- Загрузки разбираются in-process: 10 МБ на сообщение — осознанный предел для
  1–2 vCPU, а не 64 МБ из референса.
