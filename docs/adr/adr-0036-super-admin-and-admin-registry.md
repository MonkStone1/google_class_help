# ADR-0036: Super Admin, реестр администраторов в PostgreSQL, отдельная консоль `/admin`

- **Статус:** Accepted
- **Дата:** 2026-10-02
- **Заменяет:** часть ADR-0035 §2 (allow-list `ADMIN_EMAILS` как источник авторизации
  обычных администраторов)

## Контекст

ADR-0035 решил, кто отвечает на тикеты: список `ADMIN_EMAILS` в окружении,
fail-closed, только серверный. Для одного администратора этого хватало, но
развернулись три практические проблемы.

1. **Добавить администратора можно было только деплоем.** Правка `.env` и рестарт
   `web` на каждый новый человек — это операционная работа, а продуктовая
   возможность: поддержка из 2–3 человек набирается и меняется без доступа к
   VPS.
2. **Allow-list не масштабируется и не проверяет себя.** Список растёт в `.env`,
   где он не валидируется, не отображается и не имеет интерфейса. Нет способа
   посмотреть, кто сейчас администратор, и нет способа снять права без правки
   файла на сервере.
3. **Пункт «Администрирование» в общем меню показывал консоль всем, кто имеет
   право, и прятал её от остальных.** Для площадки, где консоль — отдельный
   продукт, а не «ещё один раздел», это уместнее: отдельная оболочка по `/admin`
   с собственным списком, а публичная навигация остаётся чистой.

Дополнительные ограничения, которые решение обязано учесть:

- **Аутентификация неприкосновенна** (ADR-0022): роль выводится только из
  e-mail валидной сессии; ни заголовок, ни query-параметр, ни поле формы, ни
  флаг в localStorage не имеют значения.
- **Конфигурация авторизации не должна достигать браузера** (ADR-0035): фронтенд
  получает булевы флаги, а не адреса.
- **Деплой — 1 vCPU VPS** (ADR-0028): миграция обязана применяться и к чистой БД,
  и к существующей схеме.

## Решение

### 1. Три роли

```
e-mail валидной сессии (users.email)
    ├─ == SUPER_ADMIN_EMAIL ?  → SUPER ADMIN   (strip + lower; unset ⇒ никто)
    ├─ есть строка в `admins`?  → ADMIN
    └─ иначе                    → ПОЛЬЗОВАТЕЛЬ
```

Единственный резолвер — `admin_auth.resolve_role`. `UserOut.is_admin` и
`UserOut.is_super_admin` вычисляются им же, поэтому флаги UI не могут
разойтись с вердиктом API.

### 2. Реестр администраторов — строка в PostgreSQL

Таблица `admins` (`id`, `email` UNIQUE, `created_at`), миграция `0005`.

- **E-mail — это идентичность**, хранится нормализованным (trim + lower), поэтому
  уникальный индекс и есть правило «ровно одна строка на человека».
- **Нет колонки имени**: отображаемое имя выводится сервером из адреса
  (`john.doe@gmail.com` → `John Doe`). Вторая копия идентичности расходилась бы
  с адресом, а править её незачем.
- **Нет FK на `users`** (в отличие от тикетов `0004`): администратора можно
  назначить до первого входа, а удаление аккаунта
  (`maintenance.delete_user_data`) не должно молча отзывать роль. «Сиротские»
  строки — намеренное поведение.

### 3. Super Admin — только переменная окружения

`SUPER_ADMIN_EMAIL` читается из окружения процесса, без префикса (как
`COOKIE_SECURE` / `APP_BASE_URL`), и **не является строкой реестра**. Поэтому
Super Admin нельзя удалить через UI или API: удалять нечего. Пустое, пробельное
или без `@` значение означает, что Super Admin нет (fail-closed). Смена
переменной применяется после рестарта `web` без изменения кода.

`ADMIN_EMAILS` удалён полностью: ни шеллома, ни фолбэка, ни «deprecated, но ещё
читается».

### 4. `/api/admin/admins` — только Super Admin

`GET` / `POST` / `DELETE`, все три под `require_super_admin`, который опирается на
`require_admin`, поэтому 401 живёт в одном месте. Контракт: 403 обычному
администратору и обычному пользователю, 409 дубликату и записи/удалению Super
Admin, 422 некорректному адресу, 404 отсутствующей строке. Проверка дубликата —
сначала SELECT, а поверх уникальный индекс на случай гонки.

### 5. Отдельная консоль `/admin`

`AdminShell` + `AdminSidebar` рендерятся под `/admin/*`; в публичном `Sidebar`
пункта «Администрирование» больше нет — единственный вход по URL. Обе оболочки
рисуют один presentational-компонент `SidebarNav` с разными списками пунктов, так
что разметка, активное состояние и CSS не могут разойтись (D2).

Неавторизованный `/admin` **перенаправляется** на `/`, а не показывает «недоступно»
(D10); обычный администратор с `/admin/admins` — на `/admin`. Пока ответ сессии
неизвестен (`auth === null`), перенаправление тоже: привилегированный UI не должен
мигать у того, кто грузит страницу.

## Последствия

**Хорошие**

- Добавление и снятие администратора — обычное действие в интерфейсе, без деплоя.
- Есть экран, где видно, кто администратор: реестр стал проверяемым.
- Роль Super Admin структурно неудаляема, а не «защищена проверкой в обработчике».
- Косметика публичного сайта не меняется: пользователь вообще не видит консоль.

**Плохие / ограничения**

- **Бывших администраторов из `ADMIN_EMAILS` нужно завести заново** через
  `/admin/admins`. Это сознательная разовая операция при деплое, а не
  совместимость: две схемы авторизации означали бы две правды о том, кто админ.
- Переезд `SUPER_ADMIN_EMAIL` требует рестарта `web` — переменная читается при
  импорте, как и остальные.
- Пустой реестр без `SUPER_ADMIN_EMAIL` означает, что консоль есть, а управлять
  ею некому; это заметно сразу, но «тихо» — поэтому порядок выкатки описан в
  `docs/DEPLOYMENT_CHECKLIST.md`.
