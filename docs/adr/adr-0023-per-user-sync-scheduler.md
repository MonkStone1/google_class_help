# ADR-0023: Per-user синхронизация — планировщик/воркер, `sync_status`, needs_reauth

Дата: 2026-09-20
Статус: Accepted
Связанные: [ADR-0003](adr-0003-sqlite-cache-and-sync.md), [ADR-0014](adr-0014-parallel-staged-sync.md),
[ADR-0015](adr-0015-background-sync-schedule.md), [ADR-0020](adr-0020-hosted-web-oauth-and-sessions.md),
[ADR-0021](adr-0021-postgresql-alembic-user-scoped-schema.md), [ADR-0022](adr-0022-user-isolation-get-current-user.md)

## Контекст

К этапу 5 миграции кэш уже user-scoped (ADR-0021), а каждый sync принадлежит
одному пользователю (ADR-0022). Но исполнение осталось однопользовательским:

- `sync_service._SYNC_LOCK` — мьютекс **всего процесса**: в хостед-версии
  синк пользователя B ждал бы окончания синка пользователя A (аудит Y1);
- `background_sync.py` — один глобальный цикл «синк раз в 10 минут» (S3/Y6),
  рассчитанный на единственный локальный аккаунт (ADR-0015);
- состояние синка лежит в key/value `sync_state(user_id, key)` — из него
  нельзя ответить на вопросы планировщика «идёт ли сейчас синк», «сколько
  раз подряд упал», «пауза из-за отозванного доступа?»;
- после логина синк вообще не запускался (hosted), а «синк всех сразу на
  старте» для N аккаунтов — это thundering herd (§64);
- `last_sync_error` попадал в API как `f"{Class}: {exc}"` — сырой текст
  исключения вместе с телом ответа Google (§18).

Требования промпта (§18/§19/§20/§63/§64): scheduler/worker по пользователям,
per-user concurrency control, «не давать одному сломанному токену останавливать
синхронизацию остальных», помечать пользователя `needs_reauth`, не устраивать
шторм на старте, не показывать фронтенду сырые трейсы.

## Решение

### 1. Структурированное состояние синка — таблица `sync_status` (§18)

`sync_state(user_id, key, value)` заменена одной строкой на пользователя
(`backend/models.py::SyncStatus`, Alembic-ревизия `0002`):

```
sync_status
-----------
user_id                PK, FK users.id CASCADE
status                 pending | running | ok | error | needs_reauth
last_started_at
last_finished_at
last_success_at        — то, что дашборд показывает как «last sync»
last_error             — короткая безопасная фраза (≤500 символов), не трейс
last_error_at
consecutive_failures   — вход в backoff (§63)
sync_requested         — «синкать как можно скорее» (после логина)
```

- Все переходы — через `sync_store`: `claim_sync`, `mark_sync_succeeded`,
  `mark_sync_failed`, `mark_sync_needs_reauth`, `mark_sync_pending`,
  `request_sync`. Один источник правды; фасад `sync.py` экспортирует
  `last_sync_time`/`last_sync_error`/`sync_status` вместо `get_state`.
- Таймстемпы — наивные UTC, как во всех user-scoped таблицах
  (`users.created_at`, `sessions`, `oauth_tokens`), чтобы арифметика
  «кто просрочен» не смешивала часы.
- `running` — одновременно и состояние, и **claim**: условный UPDATE
  (`claim_sync`) ставит его только если прошлый запуск не в полёте; строка,
  «висящая» дольше `SYNC_CLAIM_STALE_SECONDS`, считается упавшим воркером и
  может быть перехвачена. Это делает корректной работу нескольких воркеров
  без распределённых локов.
- `sync_requested` — флаг, а не таймстемп, намеренно: его ставит web-процесс
  (после логина), а снимает воркер — общий таймер для этого не требуется.

### 2. Per-user конкурентность вместо глобального мьютекса (§18, §20)

- `sync_now(user)` берёт **per-user** лок (`_sync_lock_for(user_id)`): два
  аккаунта синкаются параллельно, один и тот же аккаунт — никогда.
- Логика ADR-0014 сохранена полностью (общий пул на весь sync, thread-local
  клиенты, backoff 429) — добавлен только контекст пользователя: публичный
  вход `sync_user_id(user_id)` для планировщика, `sync_now(user)` для API.
- `courses.list`-ошибка, любое исключение сети и неудачный refresh
  завершаются записью в `sync_status` **этого** пользователя; остальные
  продолжают.

### 3. Ошибки — санитизированные фразы (§18)

`sync_service._public_error(exc)` маппит HTTP-статус (`resp.status`) в
короткую фразу: 401 → «sign in again», 403/429/5xx → «retry»-формулировки,
всё остальное → «Sync failed; see the server log for details». Полный
stack-trace остаётся в логе; в `last_error` и в API попадает только фраза.
Сообщение «A synchronization is already running.» зафиксировано как часть
контракта (`api.py` превращает его в 409).

### 4. Планировщик и воркер (§19, §63, §64)

Новый `backend/sync_scheduler.py`: scan → select due → bounded pool →
`sync_service.sync_user_id` → результат в `sync_status`.

- **Кандидаты** (§63): активные `users.provider == "google"`, у которых есть
  строка `oauth_tokens`, и `status != needs_reauth`. Пользователь без гранта
  в расписание не попадает вовсе.
- **Пауза и выход из неё**: неудачный refresh помечает аккаунт
  `needs_reauth` (синк сам это делает, различая «не входил» и «грант
  сломан» через `google_credentials.has_google_grant`); успешный логин
  вызывает `sync_store.request_sync` → флаг `sync_requested`, который
  снимает паузу и делает аккаунт должным немедленно.
- **Backoff** (§63): `интервал × 2^min(падений, 3)` — до 8×, чтобы
  постоянно падающий аккаунт не долбил API каждый тик.
- **Stagger** (§64): оффсет каждого пользователя детерминирован
  (`SHA-256("gch-sync-<id>")`, не `hash()` — он солёный на процесс);
  первый запуск аккаунта попадает в окно
  `min(интервал, SYNC_STARTUP_STAGGER_SECONDS)` от `created_at`, остальные
  — интервал + оффсет. Рестарт с тысячей аккаунтов не синхает всех в одну
  секунду.
- **Ограничение батча**: каждый скан подаёт не больше свободных слотов
  (`SYNC_MAX_CONCURRENT_USERS`, по умолчанию 2), поэтому даже herd из
  тысяч аккаунтов дренируется как очередь.
- **Где живёт**: выбран **Option A — отдельный воркер-контейнер**
  (`backend/sync_worker.py`, `python sync_worker.py` / `--once`). Web-процесс
  планировщик не поднимает; `GC_DASHBOARD_EMBEDDED_SCHEDULER=1` — opt-in
  для single-replica развёртывания. Celery/Redis не добавляются (§19:
  не добавлять их ради сложности). Дубликаты невозможны в обоих случаях —
  их отсекает claim в БД, а не память процесса.

### 5. API и совместимость

- `GET /api/status` и detail-ручки читают `last_sync` = `last_success_at`,
  `last_sync_error` = `last_error`; добавлены `sync_status`
  (`pending/running/ok/error/needs_reauth`), `last_sync_started_at`,
  `last_sync_finished_at`; `syncing` теперь вычисляется из статуса, а не
  всегда `false`. `frontend/src/api-schema.d.ts` перегенерирован
  (`npm run gen:api:file`), `tsc` проходит.
- `POST /api/sync` не менялся: конфликт теперь только с синком **того же**
  пользователя.
- Desktop-путь не изменён по поведению: `background_sync.py` остаётся
  одиночным циклом (в desktop ровно один аккаунт), `sync_now()` без
  аргумента — прежний вход; локальный владелец получает свою строку
  `sync_status` как любой пользователь.

## Последствия

- Синхронизация масштабируется по числу аккаунтов: параллелизм ограничен
  явно (2 пользователя × 16 воркеров по умолчанию), квота Google делится
  предсказуемо, а не «кто первый встал».
- Один сломанный грант/403 больше не влияет на остальных: у каждого джобы
  своя сессия, свои креденшелы, свой try/except (проверено тестом).
- Фронтенд получает машиночитаемый `sync_status` вместо парсинга текста
  ошибки; сырые трейсы не покидают сервер.
- Миграция `0002` **не переносит** старые ключи `last_sync`/`last_sync_error`:
  это bookkeeping кэша, который следующий синк заполняет заново. На
  PostgreSQL прод-данных ещё нет; на desktop после обновления «last sync»
  пуст до ближайшего стартового синка. Старая таблица удаляется; downgrade
  восстанавливает `sync_state` (но не структуру этапа 5).
- Оффсет-окно и claim-стайл предполагают общий таймстемп-базис у процессов
  одного деплоя (один хост/контейнеры на одном ядре с TZ=UTC); для
  мультихоста нужно выровнять TZ — зафиксировано в `.env.example`.
- Отображение `last_sync` (UTC-naive) в локальном часовом поясе браузера —
  вопрос этапа 7 (фронтенд), не этого этапа.

## Альтернативы

- Celery + Redis/RQ — отклонено (§19): на текущем масштабе это лишняя
  инфраструктура; per-user jobs + claim в PostgreSQL закрывают и
  дедупликацию, и bounded concurrency.
- APScheduler внутри web-процесса — отклонено: расписание на процесс Uvicorn,
  при нескольких репликах — дубли; встроенный режим оставлен только как
  opt-in для одной реплики.
- PgBoss / `SELECT ... FOR UPDATE SKIP LOCKED` очередь — отклонено:
  полноценная очередь задач не нужна, когда есть реляционное состояние
  синка; claim условным UPDATE проще и тестируется на SQLite.
- Случайный (не детерминированный) jitter — отклонён: `random` даст разные
  оффсеты в разных процессах; SHA-256 от id стабилен и воспроизводим.
- Хранить `sync_requested` таймстемпом — отклонено: web и воркер могут
  иметь разные TZ; флаг не требует общих часов.
