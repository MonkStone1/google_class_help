# ADR-0018: Single-instance launcher — mutex, state-файл порта, трей и активация открытого дашборда

Дата: 2026-09-17
Статус: Accepted (frontend-слой presence удалён 2026-09-25, см. ADR-0029)
Связанные: [ADR-0016](adr-0016-production-nuitka-packaging.md), [ADR-0015](adr-0015-background-sync-schedule.md), [ADR-0029](adr-0029-public-landing-page.md)

## Контекст

Exe запускается двойным кликом: он поднимает бекенд на `127.0.0.1`, отдаёт
`frontend/dist` и открывает браузер (ADR-0016). Эксплуатация выявила три
проблемы:

- повторный запуск exe (пользователь закрыл вкладку, но процесс жив, либо
  запустил ярлык второй раз) создавал **второй** бекенд: защита «порт занят и
  отвечает `/api/health`» срабатывала не всегда, а при занятом чужим
  приложением порту запуск молча уходил на следующий свободный порт;
- между двумя почти одновременными запусками была гонка: оба видели порт
  свободным и оба стартовали;
- приложение жило невидимым фоновым процессом: пользователь не понимал, что
  дашборд уже работает, и запускал exe снова — а браузер открывал дубликат
  вкладки.

Pid-файл как единственный guard не подходит: он протухает при жёстком
завершении процесса (и именно после жёсткого завершения пользователь снова
запускает exe).

## Решение

- **Именованный Windows-mutex** `GoogleClassHelp-SingleInstance` — guard
  единственного экземпляра. Второй процесс получает
  `ERROR_ALREADY_EXISTS`, не поднимает бекенд, активирует работающий дашборд и
  завершается с кодом 0. Mutex (в отличие от pid-файла) не может протухнуть:
  Windows освобождает его при смерти процесса, гонка двух запусков тоже
  закрывается ядром. Mutex session-scoped (без префикса `Global\`), чтобы
  каждая сессия Windows имела свой дашборд.
- **State-файл** `DATA_DIR/app.lock` с `{pid, port, started}` — фактический
  порт инстанса. Порт не гарантированно 8000: он занят чужим приложением —
  берётся ближайший свободный (поведение ADR-0016 сохранено). Второй запуск
  читает порт из state-файла, ждёт `/api/health` (mutex берётся до готовности
  порта, поэтому есть grace-период) и только потом активирует дашборд.
  Протухший state-файл владелец удаляет при старте и удаляет свой при
  корректном выходе.
- **Трей-иконка** вместо невидимого фонового процесса: пункты *Open
  dashboard* (двойной клик по иконке) и *Exit*; выход идёт через тот же
  graceful shutdown, что и прежде. `pystray`/`Pillow` — опциональная
  зависимость: если их нет, launcher пишет строку в лог и работает без
  иконки, дашборд не ломается.
- **Активация = фокус существующего окна.** `EnumWindows` + поиск заголовка
  из `DASHBOARD_WINDOW_TITLES` (`app.title` из `frontend/src/i18n.ts`, три
  локали), затем `ShowWindow(SW_RESTORE)` + `SetForegroundWindow` (fallback
  `SwitchToThisWindow`). Новая вкладка открывается только если окна нет.
- **Presence между вкладками (фронтенд).** В заголовке окна браузера видна
  только активная вкладка, поэтому закреплённая/фоновая вкладка с дашбордом
  для launcher невидима — в этом случае URL всё же открывается, а фокус
  возвращает сам фронтенд: первая вкладка владеет Web Lock
  (`gc-dashboard-active-tab`), вкладка, открытая позже, видит себя
  дубликатом и показывает закрываемое уведомление «дашборд уже открыт» с
  кнопкой *Switch to it*. Web Lock, в отличие от флага в localStorage,
  освобождается браузером вместе с документом и не протухает; без
  Web Locks/LockManager вкладка ведёт себя как единственная (деградация в
  ничто).
- **Переключение вкладок через service worker.** Прямой `window.focus()` из
  другой вкладки Chrome игнорирует; единственный разрешённый механизм —
  `WindowClient.focus()` из service worker (`frontend/public/sw.js`, без
  fetch-обработчика), который разрешён, пока у любого окна origin есть свежая
  transient activation — её даёт клик по кнопке. Поэтому автопопытка сразу
  после открытия вкладки может быть отклонена (это не сбой), кнопка —
  надёжный путь, а worker отвечает `focus-result`, по которому уведомление
  убирается; при отказе показывается подсказка «попробуйте ещё раз или
  закройте вкладку». В браузерах без service worker вкладка-владелец
  фокусирует себя по BroadcastChannel, где подтверждение — лучшая доступная
  оценка успеха.
- **Handshake `app.wake`.** Второй процесс не может показать balloon в трее
  первого напрямую; он создаёт файл-сигнал, владелец забирает его в своём
  цикле и показывает уведомление «уже запущено — дашборд восстановлен».

## Последствия

- Повторный запуск exe = активация работающего дашборда; второй бекенд/порт
  не появляются ни при гонке, ни после жёсткого завершения процесса. Лишняя
  вкладка не создаётся, если дашборд виден в заголовке активного окна, а
  вкладка из закреплённой/фоновой вкладки получает фокус через presence и
  сообщает об этом пользователю.
- Появились артефакты в `DATA_DIR`: `app.lock`, `app.wake` (в dev —
  `<проект>/data/`). На данные (SQLite, token) они не влияют.
- Сборка: `pystray` и `Pillow` добавлены в `backend/requirements.txt` и в
  Nuitka (`--include-package`), иначе трей молча отключится в релизе.
- ADR-0016 не пересматривается: порт 8000 или ближайший свободный, единый exe,
  тот же launcher — меняется поведение launcher при повторном запуске.
- Трей-иконка — теперь единственный видимый признак работающего приложения
  (плюс уведомление при повторном запуске).
- **Frontend-слой presence (Web Lock, BroadcastChannel, service worker) удалён
  2026-09-25 вместе с ADR-0029.** Он закрывал одну дырку — дашборд в
  фоновой вкладке не виден `EnumWindows`, — но на захощенном домене
  launcher вообще не участвует, и посетитель, открывший две вкладки,
  получал только раздражающее уведомление. Мьютекс, state-файл и
  активация по заголовку окна остались в силе: второй бэкенд по-прежнему
  не поднимается. Цена — в редком случае (дашборд в фоновой вкладке +
  повторный запуск exe) появится лишняя вкладка вместо переключения;
  это косметическое ухудшение, а не поломка.

## Альтернативы

- Pid-файл как единственный guard — отклонён: протухает при жёстком
  завершении и не закрывает гонку двух запусков.
- Фиксированный порт и отказ при занятости — отклонён: конфликт с чужим
  приложением на 8000 блокировал бы запуск дашборда полностью.
- Windows toast (`winrt`/`win10toast`) вместо balloon из трея — отклонён:
  лишняя зависимость от Windows Runtime и ещё один необязательный компонент.
- Поиск вкладки по URL через UI Automation — отклонён: хрупко к обновлениям
  браузеров, дороже в поддержке, чем фокус окна по заголовку.
- Флаг присутствия в localStorage/sessionStorage вместо Web Lock — отклонён:
  протухает при жёстком закрытии браузера и требует ручных таймаутов;
  Web Lock освобождает сам браузер вместе с документом.
- WebView/Tauri вместо браузера — отклонено ещё в ADR-0016.
