# ADR-0014: Стадийная параллельная синхронизация (общий пул на весь sync)

Дата: 2026-09-15
Статус: Accepted
Связанные: [ADR-0003](adr-0003-sqlite-cache-and-sync.md), [ADR-0010](adr-0010-student-sync-route.md)

## Контекст

Полный sync реальных данных (~700 заданий, 32 активных курса) занимал ~110 с
(см. ADR-0010). Профиль узкого места:

- курсовый цикл в `_do_sync` был **последовательным**: на каждый курс сначала
  `teachers.list`, потом `studentSubmissions.list` — это ~64 сетевых RTT
  строго по очереди;
- точечные `courseWork.get` выполнялись параллельно, но в **новом пуле на
  каждый курс** (до 8 воркеров × 32 курса): пул простаивал на границе курса,
  и каждый воркер повторно скачивал discovery-документ при построении клиента.

Квота Classroom API (1200 запросов/мин на пользователя ≈ 20 QPS) — не узкое
место; узкое место — латентность последовательных запросов. Ограничение:
решение должно масштабироваться на аккаунты с большим числом курсов и
заданий, чем у текущего пользователя.

## Решение

Три стадии в `_do_sync` (`backend/sync.py`), все сетевые задачи идут через
**один общий `ThreadPoolExecutor(max_workers=8)`**:

1. **Списки курсов** — `teachers.list` и `studentSubmissions.list` для всех
   курсов отправляются в общий пул как независимые задачи: курсы параллельны
   друг другу, и два вызова одного курса тоже параллельны.
2. **Точечные `courseWork.get`** — все пары `(course_id, work_id)`, собранные
   со всех курсов, фетчатся одним `pool.map` через тот же пул: пул не
   простаивает на границе курса.
3. **Запись в SQLite** — только в главном потоке (сессии SQLAlchemy не
   потокобезопасны), построчный upsert по первичным ключам и коммит по курсу
   — семантика кэша не изменилась.

Клиенты API по-прежнему строятся thread-local (`_thread_local_client`):
httplib2/discovery не потокобезопасны (ADR-0010). С общим пулом на весь sync
клиент строится один раз на воркер-поток (1 + SYNC_MAX_WORKERS
discovery-загрузок на sync вместо потенциальных ~8 × N_курсов при пуле на
курс).

**Квота и backoff.** Все вызовы API выполняются с
`execute(num_retries=3)`: встроенный механизм googleapiclient ретраит 429
(RESOURCE_EXHAUSTED), 5xx, rate-limit-403 и временные ошибки сокета со
случайным экспоненциальным backoff. Кратковременное превышение пер-юзерской
квоты (20 QPS) при 16 воркерах и быстром RTT поэтому не ломает sync, а лишь
замедляет его; после 3 неудачных ретраев ошибка падает в общий `except` и
попадает в `last_sync_error`, как и раньше.

**Настраиваемость.** Размер пула вынесен в `config.SYNC_MAX_WORKERS`
(переменная окружения `GC_DASHBOARD_SYNC_WORKERS`, по умолчанию 16,
некорректное значение откатывается к дефолту).

Публичный интерфейс не изменился: `sync_now()` и потоковый мьютекс — как
были; ошибка любого воркера пробрасывается через `future.result()` в общий
`except`, который пишет `last_sync_error` — поведение при сбоях то же.

## Последствия

- Сетевая часть синхронизации становится примерно в 2–4 раза быстрее: ~64
  последовательных RTT списков сжимаются до ~2 «волн» по 16 параллельных,
  а фетч coursework перестаёт терять время на пустых хвостах пулов.
- На порядок меньше скачиваний discovery-документа за один sync.
- Масштабируемость на большие аккаунты (больше курсов/заданий):
  - **Квота.** 16 воркеров × типовой RTT ≈ 10–16 QPS — под пер-юзерским
    лимитом 20 QPS; всплески гасятся backoff-ретраями. При росте числа
    заданий время sync растёт линейно (N_заданий / эффективный QPS),
    но ограничение — квота Google, а не клиент.
  - **Память.** Стадийность держит все submissions и courseWork-ответы
    в памяти до записи: для 5000 заданий это единицы МБ — приемлемо;
    при переходе на сильно большие объёмы можно вернуться к потоковой
    обработке чанков.
  - **SQLite.** Upsert по первичным ключам с коммитом на курс: транзакции
    остаются компактными при любом числе курсов; проверено смоук-тестом
    на 50 курсах × 50 заданий (2500 GET, идемпотентный второй прогон).
- Ожидаемое время sync (~700 заданий) — порядка десятков секунд вместо
  ~110 с (точная цифра зависит от RTT).

## Будущие задачи

- Ретраи и 16 воркеров — реализованы в рамках этого решения.
- Инкрементальный sync по `updateTime` — отдельное решение (см.
  «Альтернативы»): при больших аккаунтах именно он снимает линейный рост
  времени повторного sync.

## Альтернативы

- Инкрементальная синхронизация по `updateTime` — в ADR-0003 была отклонена
  как преждевременная; при 110 с на полный sync это уже не так, но решение
  требует изменения кэш-схемы и вынесено в отдельное будущее решение.
- `BatchHttpRequest` (до 1000 вызовов одним запросом) — против Classroom
  возвращал 404 (ADR-0010), хотя официальная документация API заявляет
  поддержку батчинга; заслуживает перетеста отдельным скриптом, в это решение
  не включён.
- Обработка курса целиком (включая запись в БД) в воркерах — отклонено:
  потребовало бы сессии SQLAlchemy на поток и сериализацию записи в SQLite.
- Ручное управление потоками — отклонено: `ThreadPoolExecutor` с
  thread-local клиентами уже доказал работоспособность (ADR-0010).
