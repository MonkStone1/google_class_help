# ADR-0033. Идемпотентная запись кеша: upsert вместо get-then-add

- **Статус:** Accepted
- **Дата:** 2026-09-30
- **Затрагивает:** `backend/sync_store.py`, `backend/sync_service.py`

## Контекст

Синхронизация учительского аккаунта падала с
`duplicate key value violates unique constraint "coursework_submissions_pkey"`.
Данные от Google приходили полностью, откатывалась транзакция записи, и
пользователь видел «Sync failed».

В первоначальном описании задачи причина названа напрямую: «вместо безусловного
INSERT реализовать корректный upsert». Это соответствовало симптому, но не
механике: кода «безусловного INSERT» не было — `db.get(...) is None` + `db.add()`
уже есть и выглядит идемпотентным.

## Что показала проверка

Сценарии были воспроизведены на стенде до правки кода:

| Сценарий | Результат |
|---|---|
| Первая запись курса | ок |
| Повторный прогон тех же данных | ок |
| Одна и та же submission дважды в одном payload | ок |
| **Две сессии пишут один и тот же ключ** | **UNIQUE constraint failed** |

Вывод: в пределах одной сессии `get`-then-`add` идемпотентен — identity map находит
pending-объект, и повторный прогон обновляет ту же строку. Ломает его **гонка двух
write-фаз одного пользователя**.

## Источник гонки: перехват устаревшего claim'а (ADR-0023), а не ADR-0032

Первая версия этого ADR винила ADR-0032 — кнопку «перезапустить зависшую
синхронизацию». **Это неверно, и опровергается прод-логом:**

- падение было у **планового** синка (`sync_scheduler: Scheduled sync for
  user id=2 failed`), никто рестарт не нажимал;
- трейсбек указывает `sync_service.py:506 → db.commit()`. В `HEAD` на строке 506
  находится конец сигнатуры функции, а `db.commit()` — в `HEAD~1`; там же
  `claim_is_own` не встречается ни разу (3 вхождения против 0). Значит на сервере
  была версия **без fence'а вообще**, и ADR-0032 ещё не был задеплоен.

Механизм, проверенный на стенде:

1. `next_sync_at` считает «когда синк созрел» по `last_finished_at or
   last_started_at`. У пользователя в статусе `running` это отметка
   **предыдущего** прогона, обычно суточной давности, — поэтому аккаунт выглядит
   «должным» немедленно. `select_due_users` статус `running` не отсекает.
2. Останавливает второй запуск только `claim_sync`, и лишь пока claim моложе
   `stale_after`. В `compose.local.yml` это **600 секунд**.
3. Если write-фаза учительского аккаунта длится дольше окна (сотни курсов,
   commit по каждому), её claim признаётся «мёртвым воркером», воркер
   перехватывает его и оба запуска пишут кеш.

Обе строки подтверждены отдельным тестом
(`test_a_running_user_is_due_again_once_the_window_passes`).

Отдельно, из самого лога: конфликтовавший ключ `student_id=105250506097979753968`
**отсутствует** среди 10 показанных наборов параметров из 39. Значит ORM сделал
INSERT по 39 строкам, для каждой из которых `db.get()` вернул `None` — то есть
строк в базе на момент чтения не было, и они появились до flush. Это работа
**второго писателя**, а не дубль внутри пакета.

Иными словами, дыра старше ADR-0032 и живёт в `claim_sync` с ADR-0023; ADR-0032 её
не создавал, а наоборот добавил fence — часть лечения уже была готова, когда
пришёл этот баг.

Само окно в 600 с (`GC_DASHBOARD_SYNC_CLAIM_STALE_SECONDS` в `compose.local.yml`)
и отбор пользователя в статусе `running` как «должного» **оставлены как есть**:
оба меняют поведение планировщика на проде, и решение — за владельцем
развёртывания. Оба факта закреплены тестом, чтобы при следующем инциденте не
пришлось выводить их заново.

## Решение

Две независимые половины, потому что по отдельности ни одна не закрывает
проблему.

**1. Условная запись `INSERT ... ON CONFLICT DO UPDATE`** вместо
`get`-then-`add` для всех таблиц кеша: `courses`, `course_roles`, `coursework`,
`course_students`, `submissions`, `coursework_submissions`. Проигравший в гонке
выполняет UPDATE, а не INSERT, — перекрытие не стоит ничего, и запись остаётся
идемпотентной при любом числе писателей.

Конструкт выбирается по живой сессии (`_upsert_insert`): приложение работает и на
SQLite, и на PostgreSQL, а `ON CONFLICT` у них пишется по-разному. Оба
диалекта поддерживают его давно, гейт по минимальной версии не нужен; тест
компилирует clause для обоих.

**2. Fence переносится внутрь цикла** — проверка перед каждым курсом, а не один
раз перед циклом. Плюс `db.expire_all()` перед проверкой: `SessionLocal` создан с
`expire_on_commit=False`, поэтому `db.get` внутри цикла отвечал бы из identity map
и видел бы claim, который давно освобождён, — fence, который не может сработать.

Условная запись — это защита от симптома, fence — от причины. Обе нужны: без
fence зомби-прогон продолжал бы перетирать кеш более свежими данными, а без
upsert любое оставшееся перекрытие снова роняло бы транзакцию.

## Что не изменилось

- Зеркальная чистка (`mirror cleanup`) сохранена: строки, которых Classroom больше
  не возвращает, по-прежнему удаляются. Upsert не превращается в «храним всё».
- Студенческий маршрут работает как прежде — те же строки и те же поля.
- Данные не удалялись и таблица не чистилась.
- Изоляция по `user_id` не ослаблена: конфликт всегда по полному составному
  ключу, чужая строка другого пользователя не затрагивается.

## Проверка

`tests/test_sync_upsert.py` (13 тестов) — идемпотентность повторного прогона,
обновление актуальных полей, дубли в payload, зеркальная чистка, студенческий
маршрут, изоляция пользователей, компиляция clause под оба диалекта.
`tests/test_sync_restart.py` — fence в середине цикла.

Fence-тест проверен на регрессионность: с удалённой проверкой внутри цикла он
падает, с ней проходит.

## Ограничение проверки

Гонку двух одновременных писателей на файловом SQLite воспроизвести нельзя —
второй писатель получает `database is locked`, это ограничение тестового
бэкенда, а не проверяемое поведение. Поэтому условная запись доказывается
на уровне инварианта (повторная запись по существующему ключу обновляет строку и
не плодит дубли) и компиляции SQL для обоих диалектов, а fence — тестом
на прерывание цикла. Полное гоняющее тестирование на реальном PostgreSQL с
двумя коннектами остаётся за пределами локального прогона.
