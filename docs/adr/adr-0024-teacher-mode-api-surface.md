# ADR-0024: Teacher-mode API surface — role gates, `/api/me`, identity shape и глобальный предел интерактивного синка

Дата: 2026-09-21
Статус: Accepted
Связанные: [ADR-0002](adr-0002-minimal-oauth-scopes.md), [ADR-0004](adr-0004-derived-fields-server-side.md),
[ADR-0010](adr-0010-student-sync-route.md), [ADR-0014](adr-0014-parallel-staged-sync.md),
[ADR-0017](adr-0017-teacher-mode.md), [ADR-0019](adr-0019-oauth-flow-owned-by-app.md),
[ADR-0020](adr-0020-hosted-web-oauth-and-sessions.md), [ADR-0022](adr-0022-user-isolation-get-current-user.md),
[ADR-0023](adr-0023-per-user-sync-scheduler.md)

## Контекст

К этапу 6 teacher-режим уже per-course (ADR-0017), кэш и креденшелы
user-scoped (ADR-0021/0022), синк — per-user (ADR-0023). Осталось привести
к явному контракту поверхность API и объём teacher-синка (§21–§25, §65):

- роль берётся из `CourseRole(user_id, course_id)`, но часть ручек
  (`GET /api/courses/{id}`, `.../coursework/{cw}/submissions`) отдавала
  teacher-данные без явной проверки роли — полагаясь на то, что у
  студенческого курса «не будет» ростера;
- список §23 не содержал `GET /api/me`, а `/api/auth/status` отдавал
  плоские `user_name`/`user_email` (форма desktop-loopback, ADR-0019), не
  имея канонического объекта `user`;
- teacher-синк делает заметно больше запросов, чем студенческий: ручной
  `POST /api/sync` при этом не был ограничен глобально — N одновременных
  нажатий открывали N пулов по `SYNC_MAX_WORKERS`;
- объём Google-запросов одного синка нигде не измерялся, что мешало
  ёмкостному планированию (этап 9).

## Решение

### 1. Teacher-режим: per-course роль и двойной гейт (§21)

- Роль остаётся **per-course и per-user** (`CourseRole`), единый
  булев флаг на аккаунт не вводится.
- Teacher-only данные доступны только при **одновременном** выполнении
  двух условий: аутентифицированный пользователь (существующий
  `get_current_user`, ADR-0022) **и** `role == TEACHER` для этого курса.
  Явный гейт `_require_teacher` стоит на `.../students` и `.../grades`;
  `GET /api/courses/{id}` теперь отдаёт `students` только при
  `role == TEACHER` (ранее ростер отдавался безусловно);
  `.../coursework/{cw}/submissions` обслуживает обе роли, но ветвится по
  роли: учителю — весь класс, студенту — только своя строка.
- Набор scope не меняется: четыре read-only scope из ADR-0002
  (`courses`, `student-submissions.me`, `student-submissions.students`,
  `rosters`). Write-scope'ы и доступ к почте студентов не добавляются.

### 2. Семантика — часть контракта (§22)

Миграция инфраструктуры не меняет бизнес-смысл, и это закреплено тестами:
отсутствующая оценка — не 0; teacher-агрегаты (`student_count`,
`submission_count`, `graded_count`, `average_percent`) не являются личной
сдачей учителя (`submitted`/`graded`/`points` у teacher-курса пусты);
архивные курсы скрыты во всех ручках; состояния
`not_submitted`/`turned_in`/`returned`/`graded` выводятся на сервере
(ADR-0004); один и тот же балл даёт один и тот же процент во всех
представлениях.

### 3. Поверхность API и коды ответов (§23, §24)

- Добавлена `GET /api/me` → `UserOut {id, name, email}`; нет
  аутентификации — 401 (hosted-гейт/зависимость).
- `AuthStatus` получает канонический вложенный `user: UserOut | None`;
  плоские `user_name`/`user_email` и desktop-поля (`auth_url`,
  `login_in_progress`) остаются как deprecated-совместимость до
  переключения фронтенда (этап 7).
- В ответах нет material'а Google OAuth: ни access/refresh токена, ни
  client secret, ни authorization code, ни объекта Google-креденшелов.
  Hosted-статус всегда отдаёт `auth_url = null` (loopback-URL —
  desktop-only, ADR-0019).
- Политика кодов: **401** — нет валидной сессии приложения; **403** —
  аутентифицирован, но не хватает роли курса; **404** — ресурс вне скоупа
  вызывающего (чужой курс/coursework, студент не из ростера) — существование
  чужой строки не раскрывается.
- Список маршрутов соответствует §23; дополнительные desktop-ручки
  (`/assignments/upcoming`, `/assignments/overdue`, `DELETE /cache`,
  `GET /health`) сохранены как есть, дубли не создавались.

### 4. Логин-UX: web и desktop раздельно (§25)

Hosted-вход — `GET /api/auth/login` → Google → `GET /api/auth/callback` →
сессия; loopback-callback и копирование consent-URL в логах/настройках —
desktop-механика (ADR-0019) и в hosted-UI не участвует. `POST
/api/auth/login` в hosted отвечает 405: вход выполняет браузерный редирект.

### 5. Объём teacher-синка: пределы, backoff, наблюдаемость, пагинация (§65)

- **Предел на пользователя** — общий пул `SYNC_MAX_WORKERS` на весь sync
  (ADR-0014, сохранён).
- **Глобальный предел** — `SYNC_MAX_CONCURRENT_USERS`: планировщик подаёт
  не больше свободных слотов (ADR-0023), а ручной `POST /api/sync`
  (`interactive=True`) берёт один процессный слот и при исчерпании
  отвечает **503** (фраза `SERVER_BUSY`), не накапливая пулы воркеров.
  Плановые/фоновые синки под этот счётчик не попадают: их уже ограничивает
  пул планировщика, иначе штатный джоб получал бы ложную ошибку.
- **Backoff** — `num_retries` googleapiclient на каждый запрос плюс
  экспоненциальный backoff планировщика по `consecutive_failures`
  (ADR-0023).
- **Наблюдаемость** — `classroom_api.RequestStats`: один счётчик на sync,
  общий для потоковых клиентов; в лог успеха/падения пишется
  `google_requests` и длительность. Счётчик намеренно не хранится в БД и не
  попадает в API — это операционный сигнал для этапа 9.
- **Пагинация** — все list-методы (`courses`, `courseWork`,
  `studentSubmissions` включая teacher-sweep `courseWorkId="-"`,
  `teachers`, `students`) идут по `nextPageToken` до последней страницы;
  закреплено тестом на фейковом discovery-сервисе.

## Последствия

- Teacher-данные недостижимы без роли в курсе; остаточный ростер прошлого
  «учительского» периода не вытекает через карточку курса.
- Фронтенд получает единый объект `user` и `GET /api/me`, не зная ничего о
  Google OAuth; плоские поля дадут перейти на новый контракт на этапе 7.
- Всплеск ручных синков деградирует предсказуемо (503 + повтор позже), а не
  исчерпывает Google-квоту и потоки.
- В логах появляется реальный объём запросов на один teacher-синк — входные
  данные для пересчёта `SYNC_MAX_WORKERS × SYNC_MAX_CONCURRENT_USERS`
  (этап 9).
- Глобальный предел интерактивного синка — **процессный**. При нескольких
  web-репликах каждая держит свой потолок; дедупликация одного пользователя
  всё равно гарантирована claim'ом в БД (ADR-0023). Межпроцессный предел —
  вопрос масштабирования этапа 9, а не текущего деплоя (один worker + web).

## Альтернативы

- Единый флаг `is_teacher` на аккаунт — отклонено: ломает реальную модель
  «в курсе A студент, в курсе B учитель» (§21, ADR-0017).
- Отдельный `/api/teacher/...` — отклонено: дублирует существующие
  user-scoped ручки без выигрыша; роль уже разрешается по курсу.
- Блокирующее ожидание глобального слота для ручного синка — отклонено:
  HTTP-запрос висел бы минутами; 503 с понятной фразой честнее, клиент
  повторит.
- Хранить счётчик запросов в `sync_status` — отклонено на этом этапе:
  это операционная метрика, а не состояние синка; персистенция — возможный
  шаг этапа 9 вместе с ретеншеном.
- Немедленная миграция фронтенда на вложенный `user` — отложено на этап 7
  (порядок миграции), поэтому плоские поля пока сохранены.
